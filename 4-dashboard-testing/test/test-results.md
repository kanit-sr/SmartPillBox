อัปเดตจำนวนข้างบนด้วยมือเมื่อเปลี่ยนสถานะ อัตราผ่านใช้ `PASS / (PASS + FAIL) × 100` หากยังไม่มี PASS หรือ FAIL ให้ระบุว่า “ยังคำนวณไม่ได้” และรายงาน BLOCKED / NOT RUN แยก

เกณฑ์สถานะ:

- `PASS`: ตรวจครบข้อที่บังคับในแผนและผลตรงตามที่คาด พร้อมหลักฐาน
- `FAIL`: พบพฤติกรรมไม่ตรงข้อกำหนด ระบุสิ่งที่ผิดและหลักฐาน
- `BLOCKED`: ดำเนินการต่อไม่ได้ เช่น ขาดอุปกรณ์หรือยังไม่ตกลงเกณฑ์ ระบุสาเหตุ
- `NOT RUN`: ยังไม่ได้เริ่มทดสอบ
- ถ้าเพิ่งตรวจผ่านบางส่วน ให้บันทึกส่วนที่ทำแล้ว แต่ยังไม่สรุป PASS ทั้งกรณี

| เก็บ raw data จาก Feed และ raw MQTT event log เป็นหลักฐานแยกกัน | ยังไม่ทดสอบ | NOT RUN | — |

รายการเพิ่มเติมนี้ไม่นับเพิ่มในยอด 10 กรณี แต่ต้องอ้างอิงผลในกรณีที่เกี่ยวข้องก่อนสรุป PASS

## 6. การจัดเก็บหลักฐาน

เก็บไฟล์จริงใน `test/evidence/<Run-ID>/` แล้วใส่ลิงก์แบบ relative จากไฟล์นี้ เช่น `[MQTT log](evidence/<Run-ID>/T03-mqtt.jsonl)` โดยเปลี่ยนชื่อให้ตรงกับไฟล์ที่มีจริง

- ภาพ/คลิป: การกดปุ่ม เปิดฝา ไฟ เสียง การสั่น และ LINE
- MQTT log: topic, payload JSON ดิบ และเวลาที่เครื่องบันทึกได้รับ
- Serial log: packet/ACK/seq การเข้าคิวและการระบายคิว โดยเฉพาะช่วง offline
- Feed raw data: ค่าที่บันทึกและ timestamp ของแต่ละจุด
- อ้างอิงหลักฐานการวัดใน `metrics.md` แยกจากผลผ่าน/ไม่ผ่านของ flow

ค่า `after_s` ใน `fall_acknowledged` คือเวลาจากเริ่ม alarm จนรับเหตุ ไม่ใช่เวลาหน่วงจากการคลิกปุ่ม dashboard หากต้องวัดเวลาหน่วงให้บันทึกเวลาคลิกและเวลาหยุด alarm เพิ่ม

## 7. สรุปรอบทดสอบ

- ส่วนที่ทดสอบเสร็จ: ยังไม่มีข้อมูล
- ข้อที่ไม่ผ่านและต้องแก้: ยังไม่มีข้อมูล
- ข้อที่ติดเงื่อนไขหรือยังไม่ได้ทดสอบ: T01–T10 ยังไม่ได้ทดสอบ
- ข้อจำกัดของผลรอบนี้: ยังไม่มีผลจากอุปกรณ์จริงหรือข้อมูลจำลอง
- งานถัดไป: กรอกข้อมูลรอบทดสอบ ดำเนินการตาม `test-plan.md` และบันทึกหลักฐานก่อนอัปเดตสถานะ
