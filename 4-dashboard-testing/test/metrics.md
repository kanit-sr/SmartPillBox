# Metrics

ยังไม่มีผลวัดจริง ตารางเป้าหมายเป็นเกณฑ์ของทีม ส่วนโจทย์หน้า 7 ให้เลือกวัดจริงอย่างน้อย 3 ประเภทพร้อมวิธีวัด และให้คะแนนเพิ่มเมื่อวัดซ้ำพร้อมรายงานความแปรผัน ตัวเลข 90%, 25 วิ, 5% และ 12 ชั่วโมงด้านล่างไม่ได้เป็นค่าบังคับจากอาจารย์

| ตัวชี้วัด | เป้า | วัดได้ |
|---|---|---|
| Fall detection accuracy | ≥90% บนชุดทดสอบแยกจากข้อมูลฝึก พร้อมรายงาน TP, TN, FP, FN และ recall | ยังไม่วัด |
| False positive ต่อวัน | ≤1 ครั้งต่อ 24 ชั่วโมงที่เปิดตรวจจับจริง | ยังไม่วัด |
| เวลาจากล้ม → LINE | ≥95% ของเหตุล้มที่ยืนยันและทดสอบขณะออนไลน์ ได้รับ LINE ภายใน 25 วิ รวม countdown 15 วิ | ยังไม่วัด |
| ESP-NOW packet loss / ระยะ | STATUS packet loss ≤5% ที่ระยะ 5 และ 10 เมตรในเงื่อนไขที่ระบุ ทดสอบอย่างน้อย 100 packet ต่อเงื่อนไข | ยังไม่วัด |
| แบตกำไลอยู่ได้ (ชม.) | ≥12 ชม. ต่อการชาร์จเต็มหนึ่งครั้ง ภายใต้รูปแบบใช้งานที่ระบุ | ยังไม่วัด |
| Sensor → dashboard / actuator latency | ยังไม่กำหนดเกณฑ์ตัวเลข ให้ทีมตกลงจุดเริ่ม/จบและเป้าก่อนวัด | ยังไม่วัด |
| Uptime ระหว่าง field test | ยังไม่กำหนด % เป้าหมาย; รอบเก็บข้อมูลต่อเนื่องอย่างน้อย 24 ชม. ตามแผน Field Testing | ยังไม่วัด |

## วิธีวัดที่ทำซ้ำได้

จำนวนรอบด้านล่างเป็นแผนของทีมเพื่อแสดงการวัดซ้ำ ไม่ใช่จำนวนที่ PDF บังคับ ระบุจำนวนที่ทำได้จริงและข้อจำกัด ไม่เติมผลจากการประมาณเป็นค่าที่วัดจริง

| ตัวชี้วัด | วิธี / ข้อมูลดิบ | การวัดซ้ำและการสรุป |
|---|---|---|
| AI accuracy / precision / recall | ใช้ข้อมูลทดสอบของทีมที่แยกจาก training ตาม session/ผู้เก็บ ไม่แบ่ง window ที่ซ้อนกันข้ามชุด; ระบุ ground truth, model version, จำนวน fall/normal และ TP/TN/FP/FN | วางแผนอย่างน้อย 3 session ที่อิสระ รายงานจำนวนตัวอย่างจริงและค่าราย session พร้อมผลรวม; ไม่ใช้การรันข้อมูลเดิมซ้ำแทนความหลากหลาย |
| False positive / 24 ชม. | เปิดตรวจจับกิจกรรมปกติ เก็บ prediction กับเวลาที่ตรวจสอบได้ว่าไม่ได้ล้ม แยก false detection ของโมเดลจาก false alarm ที่ผู้ใช้ไม่ได้กดยกเลิก | รายงานจำนวน FP และชั่วโมงเปิดตรวจจับจริงในแต่ละรอบ; ถ้า <24 ชม. ระบุเป็นอัตราคำนวณ ยังไม่ยืนยันเป้าเต็มวัน |
| ล้ม → LINE | `t0` = จุดเริ่มเหตุทดสอบที่นิยามไว้, `t1` = ข้อความปรากฏบนเครื่องผู้รับ; ใช้วิดีโอ/นาฬิกาอ้างอิงร่วมและบันทึก error; รวม countdown 15 วิ แยกช่วง offline และเหตุที่ถูกยกเลิก | วางแผน 20 เหตุที่ยืนยันขณะ online แบ่งอย่างน้อย 3 รอบ; `จำนวนที่ถึงภายใน 25 วิ / จำนวนเหตุที่ยืนยันและทดสอบออนไลน์ทั้งหมด`; เหตุที่ข้อความไม่ถึงต้องคงอยู่ในตัวหาร |
| Packet delivery rate / loss | บันทึก TX ของ STATUS และ RX ที่ gateway จับคู่ด้วย source MAC + boot/session + seq + type; ตัด RX ซ้ำ ไม่นับ ACK เป็น STATUS และไม่ใช้ช่องว่างของ seq เดา loss เพราะ packet ชนิดอื่นใช้ seq ร่วม | ระยะ 5 และ 10 เมตร อย่างน้อย 100 STATUS ต่อเงื่อนไขต่อรอบ วางแผน 3 รอบ; บันทึก channel, สิ่งกีดขวาง, interval; ถ้าเร่ง interval ระบุว่าเป็น test build |
| Battery life / current | ชาร์จเต็มตามวิธีที่ระบุ เปิดงานจริงจนถึงเกณฑ์หยุดที่ตกลง วัดเวลาจริง; ถ้าวัดกระแสให้วัดจุดจ่ายไฟทั้งบอร์ด ระบุเครื่องมือ แรงดัน และช่วง sample; วัดโหมด awake/sleep แยกหากเลือก E3 | วางแผน 3 รอบชาร์จเพื่อรายงาน min/mean/max; ถ้ามีรอบเดียวรายงาน 1 รอบตามจริง; ค่า estimated life จากกระแสแยกจาก measured runtime |
| Sensor → dashboard / actuator | นิยาม `t0` เป็นการอ่าน sample/เกิด trigger ที่ firmware และ `t1` เป็นค่าปรากฏบน UI หรือ output ทำงานจริง; ติด sample ID ใน log ทดสอบ ไม่แก้ schema กลางเอง; ใช้วิดีโอ/logic analyzer/นาฬิกาอ้างอิงเดียว | วางแผน 20 sample ต่อเส้นทางอย่างน้อย 3 รอบ; แสดง n, mean, min, max และ p95 ถ้ามีข้อมูลพอ; แยก sensor → dashboard กับ sensor → actuator ไม่รวมเป็นตัวเดียว |
| Uptime | ดู [field-test.md](field-test.md) ระบุว่าความพร้อมหมายถึงเส้นทางไหน เก็บ heartbeat/serial/Feed ต่อเนื่องและบันทึกช่วงที่เครื่องบันทึกเสียเอง | รายงาน duration, known-up, known-down, unknown และจำนวน reconnect; ถ้าเป็น 1 รอบ 24 ชม. อย่าอ้างว่าเป็นการวัดซ้ำหลายรอบ |

Latency ที่ได้จาก `event.ts` หน่วยวินาทีอย่างเดียวไม่แม่นพอสำหรับรายงาน milliseconds และเวลาเครื่องคนละตัวอาจเหลื่อมกัน ต้องบอกวิธี sync/ความคลาดเคลื่อน `after_s` เป็นเวลาจากเริ่ม alarm จนรับเหตุ ไม่ใช่ dashboard command latency

## สูตรและการนับ

- `accuracy = (TP + TN) / (TP + TN + FP + FN)`
- `precision = TP / (TP + FP)` และ `recall = TP / (TP + FN)`; ตัวหารเป็นศูนย์รายงาน N/A
- `FP ต่อ 24 ชม. = FP × 24 / ชั่วโมงตรวจจับที่มีหลักฐาน`
- `PDR = unique STATUS RX ที่จับคู่ TX ได้ / unique STATUS TX × 100`; `loss = 100 - PDR`
- `latency = t1 - t0` ใช้หน่วยเดียวกัน ไม่ใช้เวลา receive ที่ cloud แทนเวลาเกิดเมื่อวัด end-to-end
- ถ้าต้องประมาณแบต: `estimated hours = usable capacity (mAh) / average current (mA)` ระบุ duty cycle, ความจุที่ใช้ และสมมติฐานวงจรจ่ายไฟ แยกจากผลวัดใช้งานจริง
- ความพร้อมที่สังเกตได้: `known-up / total run × 100` พร้อม `unknown / total run × 100`; ถ้ามี unknown ผลนี้เป็นขอบล่าง ไม่สรุปว่าระบบเสียทั้งหมดในช่วงนั้น

AI accuracy กับ false positive เป็นกลุ่ม AI เดียวกัน และ latency หลายปลายทางเป็นกลุ่ม latency เดียวกัน อย่านับแยกเพื่อให้ครบ 3 ประเภทตามโจทย์ ตัวเลือกที่ตรงเกณฑ์คือ PDR + AI + battery หรือ PDR + latency + uptime เป็นต้น
